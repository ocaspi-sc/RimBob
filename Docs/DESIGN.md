---

## What is RimBob?

An AI advisor system for RimWorld. The human plays the colony; RimBob watches the live game state and sends suggestions — like a cabinet of advisors writing memos. An LLM-supported cabinet, led by the Mayor, surfaces strategic memos to a dashboard the player reads alongside the game. Ministers do not self-improve: an Oracle reviews replay, fixture, and Pushback evidence and proposes rule, prompt, briefing, or RAG changes for human approval. Over time, advice gets sharper, more advisor types come online, and individual advisors can graduate from *suggesting* to *acting* — but only when explicitly trusted by the player.

This is not an RL agent and (for the MVP) not an autonomous player. Strategy and judgment come from LLMs.
The MVP posture is **suggest + player-confirmed apply**, not suggest-only: ministers emit advice, and the player can apply a growing-but-partial allowlist of non-pawn RIMAPI writes by clicking Apply on a concrete action. Every write is gated by an explicit player click — this is not `Auto`. Write coverage is intentionally partial (far from full control); autonomous (no-click) execution remains deferred to the Auto epic.

---

## Design Goals

1. **Advise well.** Suggestions should match what a thoughtful human player would recognise as good. The player keeps control; RimBob earns trust one accepted memo at a time.
2. **Grounded in community knowledge.** Advice is informed by actual RimWorld guides, not just LLM training data.
3. **Oracle-refined from real feedback.** Accept / Dismiss / Pushback on each memo is explicit refinement evidence. The system gets better when the Oracle turns repeated evidence into reviewed rule, prompt, briefing, or RAG changes.
4. **Transparent.** Every memo carries its rationale, concrete actions, and the briefing it was based on. A single dashboard view should explain what the cabinet is recommending and why.
5. **Cheap by default.** LLMs are called only when judgment is genuinely needed. Rules handle routine; the LLM handles exceptions.
6. **Debuggable over clever.** Prefer deterministic, inspectable behaviour over emergent complexity.
7. **Suggest by default; autonomy is opt-in.** Per-minister `Off / Suggest / Auto` dial. MVP ships in `Suggest`; player-confirmed Assisted Apply is a manual click path, not `Auto`. `Auto` graduations come later, one minister at a time, behind explicit player consent.
8. **Docs capture intent, code captures detail.** Design docs record decisions, ownership boundaries, runtime contracts, and open questions. Exact class signatures, helper names, enum members, DTO fields, endpoint payloads, fixture shapes, and current rule inventories live in source and tests.

## Architecture Overview

```
┌──────────────────────────────────────────────┐
│  Advisor Layer                               │
│  Dashboard (React + TS, served by Host)      │
│  AdviceBus (SSE: AdviceItems + agenda_update)│
├──────────────────────────────────────────────┤
│  Strategic Layer                             │
│  Mayor (LLM, updates Agenda once/day)        │
│  Agenda (living plan: short+long term goals) │
│  ↓ read-only broadcast                       │
├──────────────────────────────────────────────┤
│  Cabinet Layer                               │
│  Chief of Staff + feeder ministers           │
│  Each minister: Rules → LLM escalations      │
│  Ministers read Agenda for direction         │
│  Flag Channel (cross-minister signaling)     │
├──────────────────────────────────────────────┤
│  Ingestion Layer                             │
│  RIMAPI HTTP client (read + gated apply)     │
└──────────────────────────────────────────────┘
```

> **Deferred (Auto epic):** at Auto graduation, RimBob writes the game's
> declarative automation knobs (work priorities, zones, bills, policies,
> schedules) and lets RimWorld's job-giver allocate pawns. Scope (shim, Labor,
> bulletin board, RIMAPI write coverage, allowlist) is designed at
> re-engagement, not now.

Two operational modes run in parallel:

- **Play mode** — live game loop; the Mayor updates the Agenda, while feeder ministers wake on briefing changes, evaluate rules, escalate to LLM when needed, and emit `AdviceItem`s onto the AdviceBus.
- **Oracle refinement** — async; performed by the Oracle/developer workflow, not by the play-mode minister or minister LLM. The Oracle reviews decision logs, replay records, fixtures, prompts, and human Pushbacks, then proposes changes to minister rules, system prompts, briefings, fixtures, or RAG for approval.

→ See [`design/architecture.md`](design/architecture.md) for code structure and stack.

## The Cabinet

Every minister has the same play-mode shape: a rules layer that handles routine cases, escalation conditions that trigger an LLM call, and replay/trace evidence that lets the Oracle tighten rules over time. See [`design/ministers.md`](design/ministers.md).

### MVP advisor (M1)

| Minister | Domain |
|---|---|
| **Mayor** | Daily strategic memo synthesised from colony-wide briefing. The whole MVP. |

### Feeder advisors (added M3+ as the cabinet grows)

| Minister | Domain |
|---|---|
| **Chef** | Full food chain: harvesting, farming, hunting, cooking, storage, freezer |
| **Defense Minister** | Raids, combat, fortifications |
| **Willie** | Buildings, power, layout (placement deferred) |
| **Minister of Welfare** | Mood & Needs: mood risk from needs, thoughts, recreation, schedules, relationships, guest comfort, tame-animal living-condition requests |
| **Minister of Industry** | Non-food production: stonecutting, tailoring, smithing, machining, fabrication, drugs |
| **Medical Minister** | Wounds, disease, surgery, medicine stock, hospital readiness |
| **Research Minister** | Research queue, tech path, unlock dependencies |
| **Economy Minister** | Trade, caravans, wealth pressure, surplus liquidation |
| **Chief of Staff** | Flag triage, conflict arbitration into the Mayor's digest |

### Deferred until Auto graduation

| Minister | Domain | Why deferred |
|---|---|---|
| **Minister of Labor** | Assignment solver; bulletin board clearinghouse | No consumer in `Suggest` mode or Assisted Apply — nothing allocates pawns. Re-engaged when the first feeder minister graduates to `Auto`. |

### Candidate ministers (post-MVP)

Spun out from a host minister when its rules and prompts can't keep up — e.g. ideology or prisoner-care reasoning leaving Welfare, base layout leaving Willie, animal handling leaving Chef/Welfare/Economy/Defense. Promoted case-by-case; no pre-allocated roster.

---

### Cabinet boundary rule

Each minister owns either a production chain or a well-defined subsystem. Chef owns the full nutrition chain from acquisition to cooked meals and freezer/storage integrity. Defense owns the threat-response subsystem. Willie owns built infrastructure, power, rooms, and material flow. Welfare owns Mood & Needs: mood and break-risk pressure from needs, thoughts, recreation, comfort, beauty, sleep, schedules, relationships, guest comfort, tame-animal living-condition pressure, and ideology. Guest/visitor stewardship defaults to Welfare for comfort, lodging quality, and social pressure; Economy owns trade, caravans, goodwill, and diplomacy purpose; Willie owns the physical guest-room work; Defense owns active threat response. Tame animal living conditions route through Welfare when the issue is pens, barns, animal beds, temperature-safe shelter, cleanliness-sensitive rest areas, or similar comfort/suffering evidence; Willie owns physical assets, Chef owns feed/slaughter pressure, Economy owns herd economics, Defense owns threat/combat animals, and Medical owns treatment. Chef owns nutrition-chain fixes; Medical owns treatment; Welfare owns their mood impact.

Every in-game action should eventually map to one primary owning minister. The first pass maps only clear-cut actions; contested cases are documented as open questions until their ownership is justified by actual advice/rule complexity.

## Core Principles

**Ministers output is actionable Advice.** Ministers understand what needs to be done and .

**Only the Mayor strategically**, but even the Agenda should prioritize concrete next moves. -> [`design/advice.md`](design/advice.md), [`design/ministers.md`](design/ministers.md)

**Suggest + player-confirmed apply; autonomy (`Auto`) is per-minister and opt-in.** MVP ships with every advisor in `Suggest` mode, plus Assisted Apply: the player can click to execute allowlisted non-pawn writes. This is a real, first-class — but still partial — write path, not a narrow exception, and not `Auto`: every write needs an explicit player click as the consent boundary. Graduating an advisor to `Auto` (no per-click execution) is a separate, deliberate, per-minister event gated by track record + explicit player consent. → [`design/advice.md`](design/advice.md)

**Ministers do not talk to each other directly.** All coordination is via flags. CoS arbitrates conflicts; the Mayor synthesises a daily digest. → [`design/communication.md`](design/communication.md)

**Briefings are the quality lever.** Tight, focused, ~500 tokens per minister. The state store computes derived facts so the LLM doesn't have to. → [`design/state-store.md`](design/state-store.md)

**Rules first, LLM second.** The rules layer handles the majority of decisions cheaply. The LLM earns its cost on genuine judgment calls. → [`design/ministers.md`](design/ministers.md)

> **Deferred principle (Auto epic):** *The game allocates pawns; Labor only
> recommends work-system policy.* RimWorld's work-priority grid + job-givers are
> the assignment solver. Labor never issues per-pawn job writes; at Auto it sets
> declarative policy knobs and the game executes. Until Auto graduation, no
> minister writes pawn policy at all. → [`design/ministers/labor.md`](design/ministers/labor.md), [`design/planning.md`](design/planning.md)

## External Dependencies

RimBob supports the RIMAPI fork against RimWorld 1.6 only. Old RimWorld 1.5
build targets and compatibility branches are out of scope.

**RIMAPI** — active runtime mod is the local fork at `C:\dev\RIMAPI-for-RimBob` (repo `ocaspi-sc/RIMAPI-for-RimBob`), derived from https://github.com/IlyaChichkov/RIMAPI. RimWorld mod embedding a REST + SSE server. 167 endpoints. GPL-3.0; we call over HTTP only (no linking).

**Google GenAI SDK (`Google.GenAI`)** — LLM calls via Gemini Developer API (Google AI Studio) in MVP. Same client can later target Vertex AI. Streaming for UI; non-streaming for background minister thinking.

**RIMAPI write coverage** — Full coverage is not MVP-critical. Reads must cover every briefing input. MVP Assisted Apply maps only the few allowlisted writes needed for player-confirmed actions; broad write coverage gets re-evaluated when the first minister graduates to `Auto`.

| Rules layer is table-driven (rule-as-data), one declaration per rule | Each minister's rules were written three times — executable guards in `Evaluate`, the same predicates re-evaluated in a parallel `RuleMatches` for the match trace, and a hand-maintained `AllRuleEvaluations` catalogue restating each rule's conditions/output as strings — with the stable rule id repeated across all three (and again in Willie's trace-to-request switches). Changing one rule meant editing 3-5 places and let diagnostics drift silently from behavior. The durable model is rule-as-data: each rule is one declarative record (stable id/`trace`, condition and output descriptions, match predicate, decision/escalate builder) held in a per-minister ordered list; live evaluation, the matched/suppressed trace, and the all-rules catalogue all derive from that one list. Chef already runs all-hits (landed `9357831`). Each minister's flip to all-hits is gated on those three landing in the shared base.
