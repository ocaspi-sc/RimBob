# Cabinet Run Step Dialog

## Goal

When the player clicks `Run Cabinet Now`, the dashboard opens a compact dialog immediately and shows a real log of the major manual cabinet-run steps. The log should be generated by the backend around actual work, not inferred from optimistic frontend timers.

## Current State

- `Dashboard/src/components/layout/DashboardHeader.tsx` renders the `Run Cabinet Now` button and only shows pending/error text.
- `Dashboard/src/hooks/useManualTriggers.ts` posts to `triggerCabinet()` and tracks one active manual trigger target at a time.
- `Dashboard/src/api/cabinet.ts` calls `POST /api/cabinet/trigger`.
- `Src/ApiHost/Endpoints/CabinetEndpoints.cs` returns only `triggered`, `scope`, `trigger`, `state_source`, and `used_restored_snapshot`.
- `Src/Coordination/CabinetCycle.cs` refreshes live state, falls back to a restored snapshot for eligible manual failures, then runs cabinet ministers in registry order: Chef, Willie, Mayor.
- `MinisterTraceStore` records latest per-minister traces, but there is no single run-scoped cabinet log and the SSE stream currently emits agenda/advice events only.
- There is no reusable modal/dialog component in the dashboard source.

## Product Contract

- Clicking `Run Cabinet Now` opens a small dashboard dialog immediately, even before the POST completes.
- The dialog shows timestamped major steps with status, duration when known, and one short detail line.
- Major steps are: request accepted, live-state refresh, restored-snapshot fallback when used, Chef run, Willie run, Mayor run, final complete or failed.
- Minister rows should include the trace summary after each minister completes when available: rules/LLM path, selected rule or escalation reason, advice count, flag count, and error type/message on failure.
- The dialog is inspect/debug UI, not a game-write control. Manual triggers remain suggest-only and do not execute RIMAPI writes.
- The dialog can be closed after completion; while a run is active, closing should not cancel the backend run.
- Keep the existing header pending button state so the user still sees activity if the dialog is closed.

## Backend Plan

1. Add an ephemeral `CabinetRunLogStore` or similarly named singleton under `Src/Coordination/`. It should keep a bounded latest-run/ring buffer in memory and publish an event when a run or step changes.
2. Add records for `CabinetRunLogSnapshot` and `CabinetRunStepSnapshot` with fields such as `run_id`, `scope`, `trigger`, `status`, `started_at`, `completed_at`, `duration_ms`, `steps`, `key`, `label`, `kind`, `detail`, `minister`, `state_source`, `used_restored_snapshot`, `error_type`, and `error_message`. Exact DTO names can live in source, but the HTTP/SSE contract should be snake_case like the rest of this endpoint family.
3. Thread an optional run id through `POST /api/cabinet/trigger`. The dashboard should create the id before posting so SSE progress can be correlated before the response returns.
4. Instrument `CabinetCycle.TriggerCabinetAsync` and its private run path: start the run, start/complete/fail refresh, record snapshot fallback, start/complete/fail each minister around `RunResolvedMinisterAsync`, then complete/fail the full run.
5. After each minister completes, read `MinisterTraceStore.Latest(descriptor.Label)` and copy a compact summary into the step. This keeps the dialog aligned with the existing SYSTEM trace surface.
6. Return the final `CabinetRunLogSnapshot` from `POST /api/cabinet/trigger` while preserving the current top-level fields if they remain part of the current contract. Do not add a legacy/alternate response branch.
7. Extend `/api/advice/stream` to emit a `cabinet_run` or `cabinet_run_step` SSE event from the new run-log store. Reuse the existing SSE connection instead of opening a second stream.
8. Add endpoint coverage text for the richer trigger response and the SSE event in the dashboard/system docs surface.

## Frontend Plan

1. Extend `ManualTriggerPayload` in `Dashboard/src/api/ministers.ts` or split a cabinet-specific payload type in `Dashboard/src/api/cabinet.ts` so cabinet trigger responses include the final run log.
2. Update `triggerCabinet` to accept a generated run id and pass it to the backend.
3. Extend `useAdviceFeed` to parse the new cabinet-run SSE event and expose recent cabinet run events without mixing them into advice state.
4. Extend `useManualTriggers` or add a narrow `useCabinetRunDialog` helper to create the run id, open the dialog, seed the first `request sent` step, merge matching SSE events, reconcile with the final POST response, and store any final error row.
5. Add `Dashboard/src/components/layout/CabinetRunDialog.tsx` or `Dashboard/src/components/system/CabinetRunDialog.tsx`. Use a compact native `<dialog>` or accessible `role="dialog"` shell with a close button, status header, scrollable step list, and fixed row dimensions so long error text wraps without layout jumps.
6. Render the dialog from `App.tsx` near `DashboardHeader`, passing the active/final run state and close handler.
7. Add CSS in `Dashboard/src/styles.css` for a small operations-log dialog: restrained overlay, dense step rows, clear status tones, and no nested cards.

## Compatibility And State

This is an ephemeral HTTP/SSE UI contract change, not persisted game or minister state. No compat code; wipe-and-regen on upgrade. If a generated dashboard snapshot or browser-local debug state carries the old shape, regenerate it instead of adding a legacy reader.

## Out Of Scope

- Raw Host log tailing.
- Persistent run history across Host restarts.
- Canceling a running cabinet cycle from the dialog.
- Changing the cabinet run order.
- Any new RimWorld/RIMAPI write behavior.
